# 필지 판독 커버리지 개선 (2026-09-02)

화면에서 "판독 불가" 회색 필지가 과도하게 많다는 지적을 받고 원인을 추적했다.
**설계 결함이었고, 커버리지 38.7% → 100%로 해결했다.**

---

## 1. 진단

필지 1,434,057개 중 판독 가능(`n_valid >= 3`)한 것은 **38.7%뿐**이었다.
원인은 둘이며, 큰 쪽은 우리가 만든 것이다.

| 원인 | 필지 수 | 비율 |
|---|---|---|
| 분석 마스크(경사 5° 미만 & HAND 20m 미만)에 배제 | 462,953 | 32.3% |
| 20m 격자에 픽셀 미배정 | 140,279 | 9.8% |
| `n_valid >= 3` 임계로 추가 탈락 | — | 합계 61.3% 불가 |

분류별 판독 불가 비율: **밭 78.6%**, 시설 71.2%, 과수 55.6%, 논 36.3%.

### 왜 밭이 통째로 잘렸는가

농경지 필지의 경사를 실제로 재보니 답이 나왔다.

| 구분 | 경사 중앙값 | 90분위 |
|---|---|---|
| 논 | 1.61° | 7.45° |
| 밭 | **6.16°** | 15.41° |
| 과수 | 5.45° | 14.61° |
| 시설 | 4.48° | 12.40° |

**밭의 절반 이상이 5°를 넘는다.** 경사 5° 마스크는 밭을 구조적으로 배제하는 조건이었다.

| 경사 임계 | 살아남는 농경지 |
|---|---|
| < 5° (기존) | 57.6% |
| < 10° | 82.8% |
| < 15° | 93.1° |
| **< 20°** | **97.5%** |

HAND < 20m 조건도 17.7%를 잘랐다.

### 이 마스크는 어디서 왔나

일반적인 SAR 홍수 매핑에서 지형 왜곡과 상시수역을 피하려고 쓰는 조건을
**검토 없이 그대로 가져다 썼다.** 목적이 다르다.

- 홍수 범위 매핑: 물이 고일 수 있는 저지대만 보면 되므로 급경사·고지대 배제가 타당
- **필지 상태 보고: 배제할 이유가 없다.** 고지대 밭도 젖으면 젖은 것이고,
  담당자는 그 필지의 상태를 알아야 한다

## 2. 조치

### 가. 마스크를 배제 조건에서 표기 항목으로 바꿨다

- 유효성은 `zvv`/`zvh`가 유한한지로만 판단한다 (래스터의 `valid` 밴드 미사용)
- 경사는 필지 속성으로 붙이고 **20° 초과만 신뢰도 낮음(`steep`)으로 표기**한다.
  Sentinel-1 IW 입사각이 30~45°이므로 그 이상에서 layover/shadow가 문제되며,
  20° 이하에 농경지의 97.5%가 들어온다
- HAND 조건은 제거했다
- `gee.analysis_mask()` 기본값도 경사 20°, HAND 미적용으로 바꿔 재발을 막았다

### 나. 격자에 잡히지 않는 필지는 대표점에서 읽는다

20m 격자에서 9.8%는 픽셀을 하나도 배정받지 못했다. 팜맵 필지 평균이 1,500 m²
(약 39m × 39m)라 인접 필지에 밀리면 사라진다.
이 경우 폴리곤 내부가 보장된 대표점 한 곳을 읽고 `method="point"`로 구분한다.

**면적 비율과 점 표본을 같은 숫자로 섞지 않는다.** 근거의 등급이 다르므로
`method`와 `n_valid`를 함께 저장해 화면과 문서에서 구분한다.

### 다. 판독 해상도를 20m → 10m로 올린다

Sentinel-1 GRD는 원래 10m다. 20m는 우리가 스스로 버린 해상도였다.
10m에서는 필지당 픽셀이 4개에서 약 15개로 늘어 격자 미포착과 표본 부족이 함께 줄어든다.
(`notebooks/export_10m.py`)

## 4. 화면이 필지를 전혀 불러오지 못하던 버그

커버리지를 고친 뒤에도 지도에 필지가 하나도 뜨지 않았다. 자료 문제가 아니었다.

`parcel_index.json` 에 **bbox 가 빠져 있었다.** 화면은 지도 중심이 어느 읍면동에
드는지를 이 bbox 로 판정하는데, 인덱스에 `emd_cd`/`n`/`kb` 만 들어 있어
`e.bbox[0]` 이 예외를 던지고 필지 로딩이 조용히 중단됐다.
`build_parcel_tiles.py` 가 bbox·읍면동명·시군명을 함께 기록하도록 고쳤다.

여기에 브라우저 캐시가 겹쳤다. 인덱스를 고쳐 쓴 뒤에도 브라우저가 옛 파일을 계속
읽어 같은 증상이 남았다. 자료 파일은 갱신 주기가 짧으므로 `cache: "no-cache"` 로
받는다. **자료 갱신이 화면에 반영되지 않는 실패는 조용해서 더 위험하다.**

수정 후 부여읍에서 필지 10,575개가 로드되고 판독값 결측은 0개다.

## 5. GEE 무료 티어가 restricted mode 로 내려간 뒤

다년 침수 빈도를 새 마스크로 다시 뽑으려는데 GEE 가 거부했다.

    400 User memory limit exceeded

관측마다 day-of-year 정합 baseline(median + MAD)을 만드는데 MAD 는 컬렉션을 두 번
훑는다. 관측 21건이면 baseline 21개가 한 그래프에 들어간다. 아침에는 통과하던 요청이
무료 티어 compute quota 초과로 restricted mode 에 들어간 뒤로는 **4건짜리도** 실패했다.
실측으로 한계를 재어 보니 2건까지 통과한다.

그래서 빈도 합산을 GEE 에서 로컬로 옮겼다. 관측을 2건씩 끊어 `n_flag`/`n_obs` 만
받아 오고 빈도는 로컬에서 계산한다(`build_susceptibility_v2.py`). 부분 파일이 남아
있으면 건너뛰므로 중간에 끊겨도 이어받는다. 전송 실패(429/5xx)에는 지수 백오프
재시도를 붙였다 — 10m 재수출이 일시적인 503 하나로 통째로 죽은 적이 있다.

**외부 연산 자원의 한계는 고정값이 아니다.** 어제 되던 크기가 오늘 안 될 수 있으므로
한 번에 다 보내는 구조 대신 나눠 보내고 이어받는 구조로 둔다.

## 6. 다년 침수 빈도 재생성의 규모를 실측으로 정했다

관측 2건짜리 요청 하나가 타일 45개, 타일 하나가 약 1분이다. 조건을 충족하는 관측을
전부 쓰면 젖은 21건 + 마른 165건 = 93개 요청, **70시간**이 걸린다. 못 쓴다.

세 가지를 줄였다.

| 조정 | 근거 |
|---|---|
| 타일 45 → 32개 | 충남 bbox 는 서해를 크게 물고 있다. 도 경계에 닿지 않는 13타일은 요청하지 않는다 |
| 젖은 관측 21 → 12건 | 3일 누적강수 상위 12건. 실험 05 의 라벨은 관측 2건에 ROC-AUC 0.629 였다 |
| 마른 관측 165 → 8건 | 대조군이므로 오탐 여부를 가릴 수 있으면 된다 |

마른 관측은 **젖은 관측의 day-of-year 범위 안에서** 골랐다. 실험 02 에서 6월 영상을
7월 baseline 과 비교하면 생육단계 차이가 그 자체로 이상치가 된다는 것을 확인했으므로,
계절이 어긋난 대조군은 대조가 아니라 잡음이다.

결과적으로 10개 요청 × 32타일 ≈ 5시간으로 줄었다.
**연산 자원이 제한되면 방법을 줄이는 것이 아니라 표본을 줄인다.** 마스크로 필지를
잘라내는 것과 달리 관측 수를 줄이는 것은 결론의 방향이 아니라 라벨의 분산에만 영향을 준다.

## 7. 값이 없는 필지가 "대표점 표본"이라고 주장하고 있었다

커버리지를 100%로 올린 뒤 제안서에 쓸 숫자를 검산하다 발견했다.

`parcel_stats_v2` 는 격자에 화소가 없는 필지를 일단 `method="point"` 로 표시한 뒤
대표점을 읽는다. 그런데 **대표점마저 유효하지 않은 필지 12,510개(0.87%)** 는
`n_valid=0` 인 채로 `method="point"` 가 남았다. 타일 생성기는 `method` 만 보고
화면 표기를 정했으므로, 이 필지들은 값이 없는데도 **"대표점 표본"이라는 근거를
주장하고** 있었다.

이 제안의 설계 원칙은 "근거 없는 결과를 내지 않는다"이다. 근거가 없는 것을
근거가 있다고 표시하는 것은 같은 원칙을 정반대로 어긴다.

- `parcel_stats_v2`·`parcel_means_v2`: 대표점도 실패하면 `method="none"`
- `build_parcel_tiles`: `n_valid<=0` 이면 `method` 와 무관하게 판독 불가로 표기

| 표기 | 필지 | 비율 |
|---|---|---|
| 면적 집계 | 1,282,286 | 89.42% |
| 대표점 표본 | 139,261 | 9.71% |
| **판독 불가** | **12,510** | **0.87%** |

기획서와 화면의 "10.6%"를 9.7%로 고치고 0.9%를 명시했다.
**100%라고 말하고 싶어서 반올림한 것이 아니라, 분류가 틀려서 100%로 보였던 것이다.**

## 8. 로컬 집계와 수출을 같이 돌리면 둘 다 죽는다

수출이 네트워크를 기다리는 동안 CPU 가 논다고 판단해 `build_event_labels_v2.py` 를
함께 돌렸다. 둘 다 MemoryError 로 죽었다.

- 필지 인덱스 래스터화는 6201 x 9462 격자에 **830MB 를 한 번에 요청**한다
- GEE 직렬화는 연산 그래프를 파이썬 객체로 펼치며 그만큼을 또 쓴다
- 남은 물리 메모리는 4GB 였다

**이 파이프라인의 병목은 CPU 가 아니라 메모리다.** 수출 중에는 로컬 집계를 돌리지 않는다.

건진 것 두 가지.

**부분 결과가 남아 재개됐다.** `freq_parts/` 에 wet 6개와 dry 2개가 있었으므로
다시 실행하니 dry 3번째부터 이어갔다. 청크로 나눈 설계가 여기서 값을 했다.

**야간 체인이 넘어가지 않았다.** 수출 프로세스가 사라진 동안에도 후속 단계를 시작하지
않았는데, 종료 판정에 연속 3회 확인을 요구해 둔 덕분이다. 단일 확인이었다면
부분 결과로 마무리하고 진짜 완료 때는 아무도 다시 만들지 않았을 것이다.

## 10. 백분율이 표본 크기를 감추고 있었다

발표가 없는 공모전이라 화면이 스스로 설명해야 한다는 전제로 필지 상세를 다시 읽다가
드러났다. 화소 2개짜리 필지의 침수율이 **"50.0%"** 로 적혀 있었다.

화소 수 분포를 재 보니 문제의 크기가 나왔다.

| 구간 | 면적 집계 필지 중 비율 |
|---|---|
| 화소 1개 | **11.9%** |
| 화소 2개 이하 | 26.8% |
| 화소 4개 이하 (중앙값) | **50.2%** |
| 화소 10개 이하 | 84.5% |

팜맵 필지는 평균 1,500 m²(약 39m × 39m)라 20m 격자에서 화소가 몇 개 나오지 않는다.
**면적 집계 필지의 절반이 화소 4개 이하이고, 11.9%는 화소가 1개다.**
화소 1개짜리는 `method="area"` 로 적혀 있지만 근거의 두께는 대표점 표본과 같다.

소수점 한 자리 백분율은 그 사실을 감춘다. 화소 2개에서 나온 값은 0·50·100 셋 중
하나뿐인데 "50.0%" 는 필지 전체를 재서 얻은 비율처럼 읽힌다.

### 표기를 표본 크기에 맞췄다

| 화소 수 | 표기 |
|---|---|
| 1개 | **침수 / 비침수 판정** (비율이 성립하지 않는다) |
| 2~10개 | **화소 2개 중 1개 (50%)** |
| 11개 이상 | 81.8% |

이용 안내에도 이 한계를 적었다. **표본 크기를 감춘 백분율은 실제보다 정밀해 보인다.**
같은 이유로 관측 없음을 0%로 적지 않기로 했던 것과 같은 원칙이다.

10m 재수출이 끝나면 필지당 화소가 약 4배로 늘어 이 문제 자체가 줄어든다.
